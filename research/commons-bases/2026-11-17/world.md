# A commons and its units: who holds what, how the commons learns (2026-11-17)

Read: Linux MAINTAINERS (docs.kernel.org/process/maintainers.html: one file of fixed fields M R L S T F...; the status per unit - Supported, Maintained, Odd Fixes, Orphan, Obsolete - is declared in the commons' file and goes stale with the last edit; get_maintainer.pl derives who to mail from F patterns, nobody keeps a per-file list); devicetree bindings vs board dts (docs.kernel.org/devicetree/bindings/writing-bindings.html: the commons holds YAML schemas, each board its own dts; a board not validated is untested, not wrong); Debian Ports wiki (wiki.debian.org/Ports: hub page plus a status template, one subpage per port made from the template, status typed by hand and able to drift); Debian package tracker (tracker.debian.org: shows everything per package; its data is pulled from archive/BTS/VCS - from memory); Renovate (docs.renovatebot.com/key-concepts/how-renovate-works: a pull model - scan repositories, find manifests by name, derive, open PRs); GitHub template repositories (docs.github.com: a repository made from a template has unrelated history, no link back, no later updates; a fork keeps history); Copier (copier.readthedocs.io/en/stable/updating: .copier-answers.yml records the template version; copier check-update reports units that lag).
Not read: postmarketOS (wiki and GitLab redirect to nura.eco; pmaports device-*/soc-*/firmware-* packages and main/community/testing categories and the wiki Features table are from memory), Fedora ARM (Anubis block), Wikidata/OSM, nixpkgs vs flake inputs, submodules/subtrees, feed aggregation.

Common shape: the commons holds schema, rules and process; each unit holds its files and its own claim of status in a fixed machine-readable shape; the commons learns by pulling (files' metadata, CI, a registry) and derives a summary - it does not keep a second typed copy. Copies drift where status is typed twice. Stale units must show as "not known yet", not as green.
Options weighed for 'a commons base plus one open base per device': A the unit declares status in a fixed shape, the commons pulls and derives (Renovate/MAINTAINERS style; cost low); B = A plus Copier-style template updates and a lag report (medium); C derive from evidence by CI results (high: a phone cannot run in CI).

Here, measured in linux-phone-oco/docs on 2026-11-17: 2.0 MB of data, of which test_results.json 1.3 MB (device measurements); docs' own project holds 81 backlog items of which 40 name a device, 49 research rows of which 34, 28 decisions of which 14, 46 log entries of which 21; surya-lab (16 backlog, 12 decisions, 8 research, 31 log) and google-walleye-lab (11, 1, 4, 1) are filed in docs too; the phone keeper lands to docs every few minutes, and a landing that touches data/backlog.json conflicts whole-file with another (seen repeatedly; replay by records). docs PR 260 (the coordinator) added a `device` field to backlog and `tad q lane-next --device D`: it tells lanes apart but not the weight or the conflicts.
