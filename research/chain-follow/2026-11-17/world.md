What idealkb's mechanism is (read in the repo): bin/follow.sh BASE VERSION lays the files named in `generic` (statements whole; AGENTS.md and tables.toml between idealkb:begin/end) from a tagged release, keeps the files a base names `own`, and ends 3 when the base had changed a generic file (the diff is the signal to send it upstream); bin/update-pins.sh does this weekly for `consumers` through land, so each base's own CI decides; a release is tagged only when every consumer answers the five generic queries with it laid (the followers gate). It is source-agnostic: it reads `generic` and tags from whatever clone it is run in.
Fit: the thing that flows is a SLICE of files laid into a repository that also holds its own data and own files - not a whole repository. A fork of idealkb (a rhizcut) would carry idealkb's crate, release machinery, data and research into every device base, and a base cannot be a fork of both idealkb and device-template; a subtree needs a directory prefix, while tad reads queries/, records/ and tables.toml at the base's root; Copier/cruft are Python (no new Python) and keep a second answers file beside the pin; Renovate bumps a number but does not lay the files. rhizoid does fit where a whole repo is forked to be patched and kept in step: linux-phone-oco/linux is a fork of sm7150-mainline/linux (a true cutting), and tad-engine or argenv would be if patched - and rhizoid lacks, for slices, a consumption mode (a file list taken from a pinned release into a repo with an own-list and a drift verdict: follow.sh is its prototype).
